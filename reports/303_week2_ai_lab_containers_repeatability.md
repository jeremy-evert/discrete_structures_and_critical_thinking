## 4. Tuesday local-AI evidence workflow

The current Windows source verifies these action names and order: `Check`, then when READY, `Baseline`, `Launch`, `Diff`, and `Final`; `Reset -ConfirmReset` is the disposable recovery action. The DSCT package does not rename or reimplement them.

The evidence boundaries are explicit:

- command resolution supports “the command was found,” not complete functionality;
- a loopback API response supports reachability at that moment, not answer quality;
- a listed model supports reported availability, not successful inference;
- `READY` supports the readiness checks at that moment, not correctness;
- Aider completion supports a request/proposal event, not a justified change;
- `Diff` supports what text changed, not that the change is correct;
- `Final` supports the supplied test expectation for its tested cases, not every possible input or a general theorem.

## 6. Tuesday NOT READY fallback

An accurate `NOT READY` result is successful evidence practice when institutional setup is unavailable. Students retain the status and first diagnostic code, do not install/download/repair, and use a sanitized instructor or partner receipt to practice interpretation. They may claim what the supplied evidence demonstrates, but not that their own machine was READY. This preserves the learning objective without converting infrastructure failure into student failure.
